# Localized Rain 2.0.0-alpha 开发计划

> 状态：草案（2026-11-20），等待确认后按阶段实施。
> 基线：工作区 1.9.0-alpha（未提交），协议版本 `"9"`，`HEAD 4b5acae`。
> 目标版本：`2.0.0-alpha`（内容量大；如需按小步推进，可拆成 `1.10.0-alpha` + `2.0.0-alpha`）。

## 0. 需求与结论先行

用户提出四条需求：

1. 风暴增加地形交互能力、生命周期事件、合并/分裂。
2. 所有内置包天气加渐变效果（风暴与片模式）；天气传播先出详细设计；分析室内隔离缺陷。
3. 天气预报：云图 GUI（按键打开），或与 Xaero 世界地图联动；预报集成在 GUI 中。
4. 兼容：增加 API、与其他模组联动（不着急）、effects 允许修改任意属性、分析 Apothic Attributes 可行性。

补充反馈（2026-11-20）：

- **室内外能见度是否分开计算**：室外大雾正常影响能见度、室内不起雾；若性能开销巨大则不做。
- **Xaero 世界地图**：希望从 GitHub 下载最新源码并基于该库联动。
- **生命周期**：天气能否根据参数在后续演化出多种可能天气？片模式能否也有生命周期效果？

结论：

| 议题 | 结论 |
| --- | --- |
| 室内外能见度 | **可做且开销很小**：按相机位置算 `exposure`（室内 0 / 室外 1，含“窗口”探测），只缩放天气雾、天气天空色、粒子数、雨声音量；**不做**体积雾/穿窗可见雾（需要 shader，成本与兼容性都不可接受）。 |
| Xaero 源码 | **Xaero 的模组闭源，GitHub 没有官方源码库**（只有社区附属模组如 XaeroPlus、XaeroWorldMapVisualExtras 开源）。替代路径：Xaero 官方 Maven 发布完整 jar（含 1.21.1 1.47.0），且 jar 内有公开扩展 API（`WorldMap.mapElementRenderHandler` + `MapElementRenderer`/`MapElementRenderProvider`），可 `compileOnly` 依赖该坐标、按 API 编写，**不复制/不打包** Xaero 代码。 |
| 生命周期/演化 | 支持：风暴阶段加“分支演化表”（按温度/水分/权重选择下一阶段，可换天气类型）；片模式加 `lifecycle`（进入/衰退曲线）与 `next`（按权重演化到其他类型），两者共用 `WeatherType` 定义。 |
| 版本 | **已确认 `2.0.0-alpha`**；协议 `"9"` → `"10"`（新增云图 payload）。 |

## 2. WP1：风暴深度（地形、生命周期事件、合并/分裂、演化）

### 2.1 生命周期事件（新增 3 个 pre 事件）

| 事件 | 可取消 | 字段 | 用途 |
| --- | --- | --- | --- |
| `StormDyingEvent` | 是 | `level`, `snapshot`, `cause`（`FINISHED/FAR_AWAY/MANUAL/CLEARED/MERGED/SPLIT`） | 阻止本 tick 开始淡出（护盾、图腾、保护插件） |
| `StormMergeEvent` | 是 | `level`, `snapshotA`, `snapshotB` | 阻止合并 |
| `StormSplitEvent` | 是 | `level`, `snapshot`, `childCount` | 阻止分裂 |

- `StormRemoveEvent.Reason` 增加 `MERGED`、`SPLIT`。
- 派发方式沿用 `StormManager.tick` 现有“循环内收集、循环后统一 post”，避免 CME。
- 文档明确：新事件只做 pre；post 状态仍由 `StormRemoveEvent` / `StormStageChangeEvent` 表达。

### 2.2 地形交互（新类 `storm/StormTerrain.java`）

- 采样频率：每风暴每 `terrainSampleIntervalTicks`（默认 40）一次；采样 5 点：中心、上风 `c - dir*0.6R`、下风、左右横风；高度用 `Heightmap.Types.MOTION_BLOCKING_NO_LEAVES`（O(1)，不加载区块）。
- 产出三个临时因子（不存档，重算）：
  - `rainFactor`：迎风坡抬升 → `1 + orographicGain * slope`；背风干燥 → `1 - leewardDrying * slope`；clamp `0.25..2.0`。
  - `speedFactor`：上坡/峭壁减速，下坡微加速；clamp `0.3..1.2`。
  - `steer`：垂直风向的高度梯度把风矢量往低处偏转（`terrainSteer`），让风暴绕高地走。
- 生效点：`StormObject.tick` 的速度乘 `speedFactor`；`baseRain/baseThunder` 乘 `rainFactor`；`BAND`/洞穴风暴与 `manual` 风暴跳过（`terrainAffectsManual` 默认 false）。
- 成本：每 40 tick 每风暴 5 次 `getHeight`；8 风暴/维度 ≈ 1 次/tick，可忽略。
- 明确不做：真正的寻路/绕山算法（成本高、需求不明）；只在运动学层面近似。

### 2.3 合并 / 分裂（新类 `storm/StormMerger.java`）

**合并**：每 `mergeCheckIntervalTicks`（100）检查一次。

- 条件：同维度、都非 dying、类型相同或 `typesCompatible`、`dist <= (r1+r2)*mergeRadiusFactor`（0.6）、非 manual（`mergeManual` 默认 false）、冷却 `mergeCooldownTicks`（200）。
- 结果：保留更老/更大者；位置面积加权；`radius = clamp(sqrt(r1²+r2²), profile.min, profile.max*1.5)`；雨/雷面积加权；阶段取较靠后；速度加权；另一个以 `Reason.MERGED` 移除；发 `StormMergeEvent`（取消则跳过）；广播。

**分裂**：每 `splitCheckIntervalTicks`（100）检查一次。

- 条件：`radius > profile.radius.max()*splitRadiusFactor`（1.4）、非 dying/manual、随机 `splitChance`（0.25）、维度风暴数 < `maxStormsPerDimension`。
- 结果：父风暴半径缩到 0.62、强度 0.9；生成 1 个子风暴于垂直风向 ±0.55R，半径 0.55R、强度 0.85、速度 = 父速度 ± 0.4×横风分量；子风暴 `lastTransitionFrom` 记为 `SPLIT`；发 `StormSplitEvent`（取消则跳过）；**不删除父风暴**（避免“风暴突然消失”）；`data.setDirty()` + 广播。
- **分裂后合并免疫**：父子风暴在分裂瞬间距离仅 `0.55R`，而合并阈值是 `(0.62R + 0.55R) × 0.6 ≈ 0.70R`，若不加限制，下一次合并检查就会把它们合回去，分裂等于没发生。实现：`StormObject.mergeImmuneUntil`（持久化 `merge_immune_until`），分裂成功时父子都设为 `now + mergeImmunityTicks`（默认 1200 tick = 60 秒）；`mergePass` 跳过任一方仍在免疫期内的组合。合并冷却与免疫相互独立（冷却限制“多久能再合一次”，免疫限制“谁不能参与合并”）。
- 两者只在 MOBILE 模式执行；隔离群系的 manual-only 规则沿用。

### 2.4 风暴演化分支（用户需求 3 前半）

在 `StormProfile.Stage` 上增加可选 `transitions`（缺省 = 现有线性推进，旧数据包完全兼容）：

```json
{
  "stages": [
    {
      "type": "localizedrain:shower",
      "min_ticks": 1200, "max_ticks": 2400,
      "rain": [0.4, 0.8],
      "transitions": [
        { "stage": 1, "weight": 6, "min_moisture": 0.5 },
        { "stage": 2, "weight": 3, "min_temperature": 0.6, "min_moisture": 0.7 },
        { "stage": 3, "weight": 1 }
      ]
    }
  ]
}
```

- 选择逻辑：在 `StormEvolution` 的“阶段推进”时机（计时到期或 `advance_when_moisture` 触发）按权重抽一条 **条件满足** 的 transition；无满足项则回退线性下一阶段；已是末阶段则进入淡出。
- 条件：`min_moisture` / `max_moisture` / `min_temperature` / `max_temperature`（复用现有 `storm.moisture`、`storm.temperature`）；可选 `type` 覆盖目标阶段的天气类型（不写则用目标阶段自带 type）。
- `stage` 索引 sanitize：越界钳到末阶段；`weight` 下限 1、上限 1e6。
- 客户端：阶段切换沿用 `StormStageChangeEvent` + 能力位刷新（`refreshCapabilities` 已实现），`StormSyncPayload` 无需改结构。

## 3. WP2：天气表现（渐变、室内外、片模式生命周期、传播设计）

### 3.1 全类型渐变（新类 `client/ClientWeatherTransitions.java`）

- 记录变化前层（`typeId → intensity/typeKey`）作为 `from`，新层作为 `to`；持续 `weatherTransitionTicks`（CLIENT 默认 40 = 2s），逐层 lerp；union 处理新增/消失类型。
- 片模式（`ClientWeatherTargets` 单层）与移动模式（`ClientWeatherLayers` 多层）共用；雾、天空、粒子、音效都从混合层读取。
- 快速连续切换：以当前混合结果作为新 `from`；登出/换维度立即清零；`0` = 关闭（现行为）。
- CLIENT 配置（新 `client.toml`，`[visual]`）：`weatherTransitionTicks`(40, 0–200)。

### 3.2 室内外能见度分离（反馈 1）

**可行性**：Minecraft 的雾是“每帧一个相机全局 near/far/color”，没有体积雾；要让“透过窗户看室外雾”只能上 shader，成本高、兼容差 → 不做。但“室外有雾、室内没雾”可以低成本实现。

**方案**：

- 每帧计算 `exposure`：
  - `level.canSeeSky(cameraBlockPos)` 为 true → `1.0`；
  - 否则做 4 个水平相邻格 + 上方 1 格的“窗口探测”，任一可见天空 → `0.5`（半遮挡）；否则 `0.0`。
  - 全帧最多 6 次 `canSeeSky`，开销可忽略。
- `exposure` 统一缩放：天气雾色/雾距（`applyFogColor`/`applyFogPlanes`）、天气天空覆盖（`WeatherSky`）、粒子数量（在 `spawnParticles` 乘 `exposure`，并对每个候选生成点做一次 `canSeeSky`）、雨声音量（乘 `exposure`）。
- 原版/流体雾（水、岩浆、细雪）不受影响；室内完全无天气雾，但保留原版环境雾。
- 限制写进 README：不做体积雾/穿窗可见雾；半遮挡按 1 格窗口探测近似。

**原版雨声的室内处理（已核实源码，非引擎自动遮挡）**：`LevelRenderer#tickRain`（1.21.1，430-485 行）在玩家周围 ±10 格随机取雨点，若该雨点位于玩家头顶之上（`blockpos1.getY() > 玩家Y + 1` 且所在列 MOTION_BLOCKING 高度图高于玩家 Y），播放 `SoundEvents.WEATHER_RAIN_ABOVE`（音量 0.1、音高 0.5），否则播放 `SoundEvents.WEATHER_RAIN`（0.2、1.0）；两者都是带距离衰减的**位置音效**。也就是说，“室内能听到淡化雨声”是原版用「屋顶上方雨声变体 + 距离衰减」模拟出来的，不是引擎做了遮挡。

因此本模组拆成两个系数，避免“室内一律静音”比原版更突兀：

- `indoorVisualFactor`（默认 0）：只作用于雾色/雾距/天空覆盖/粒子数量。
- `indoorSoundFactor`（默认 0.35）：作用于天气环境音音量；`exposure < 0.5` 时再把音高乘 `0.6`（模仿 `WEATHER_RAIN_ABOVE` 的“闷”感）。自定义类型没有 above 变体，只降音量与音高。

CLIENT 配置：`indoorVisualFactor`（0.0，0–1）、`indoorSoundFactor`（0.35，0–1）。

### 3.3 片模式生命周期 + 演化（用户需求 3 后半）

数据格式（`weather_type` JSON，均可选，旧包兼容）：

```json
{
  "lifecycle": { "ramp_in_ticks": 200, "ramp_out_ticks": 400 },
  "next": [
    { "type": "localizedrain:thunderstorm", "weight": 4, "min_biome_temperature": 0.5 },
    { "type": "localizedrain:overcast",     "weight": 2 }
  ]
}
```

- `lifecycle`：片状态存在时间内的强度曲线（`ramp_in` 线性上升、`ramp_out` 线性下降），乘到 `rainLevel/thunderLevel`（以及发给客户端的 intensity）；0 表示不启用。
- `next`：当前类型“寿命到期”时，按权重抽下一个类型（先过滤：目标必须已注册、在当前片允许的池里、未被黑名单/锁定阻止；无满足项则回退现有 pool 抽样）。
- 实现点：`WeatherData.WeatherState` 增加 `ageTicks`（持久化，`DATA_VERSION` 12 → **13**，旧档 age 从 0 开始）；`WeatherState.tick` 在类型切换分支使用 `next`；强度曲线在 `effectiveLevel` 计算处乘系数。
- 条件字段：`min_biome_temperature` / `max_biome_temperature` / `biome_tag` / `dimension` / `requires_skylight`（至少支持前三个；后两个复用现有 `SkylightMode`/`DimensionSelector` 语义）。
- 强制/锁定片（`forced`/`locked`）不参与演化；`/weather type` 手动设置也不演化（写入 `manual` 标记）。
- 配置（SERVER `[patches]`）：`patchWeatherEvolution`（true）、`patchLifecycle`（true）。
- 客户端渐变（3.1）会自动把类型切换做成淡入淡出，不需要额外协议。

### 3.4 天气传播设计文档（只交付设计）

新建 `docs/weather-propagation.md`，包含：

- 模型：patch 图 + 风向 8 向步进（`propagationStep` 1–4 片）、`propagationChance`、`propagationDecay`、`propagationMaxAge`。
- 只对已加载片、跳过 manual/forced/locked；按风向排序扫描避免双向抖动；每 sweep 上限 64 次传播。
- 数据：`WeatherState` 预留 `origin`/`age`（与 3.3 的 `ageTicks` 共用）；`DATA_VERSION` 13。
- 观测：`/weather debug propagation`；失败回滚开关 `propagationEnabled=false`。
- 测试矩阵：单向推进、绕山、两片互推、手动覆盖、存档重载。
- 该文档批准后才进入实现（不在本计划范围）。

## 4. WP3：天气地图（自有 GUI + Xaero 世界地图联动）

### 4.1 自有云图 GUI

- 键位：`key.localizedrain.weather_map` 默认 **`K`**，类别 `key.categories.localizedrain`；`LocalizedrainClient` 注册 `RegisterKeyMappingsEvent`，`ClientTickEvent` 里 `while (consumeClick()) setScreen(new WeatherMapScreen())`。
- `client/gui/WeatherMapScreen extends Screen`：地图面板（可缩放、玩家箭头、片 16×16 着色 = 类型色 × 雨量 alpha、风暴圆 + 半径 + 类型色、风矢量、图例）+ 右侧预报列表（未来 60s 变化：当前类型→下一类型、倒计时、雨/雷条）。
- 数据：`WeatherMapRequestPayload`（C2S，空，10 tick 限流）与 `WeatherMapPayload`（S2C）：
  - `PatchView(long packedCenter, ResourceLocation typeId, float rain, float thunder, int rainTicksLeft, int thunderTicksLeft, boolean forced, boolean locked)`；
  - `StormView(UUID id, double x, double z, double vx, double vz, double radius, ResourceLocation typeId, float rain, float thunder, int stageIndex, int stageCount)`；
  - `WindView(float vx, float vz)`；`long gameTime`；半径上限 `MAX_PATCHES=512`、`MAX_STORMS=64`，decode 校验。
- 服务端 `weather/WeatherMapService`：按玩家半径（64–1024，默认 512）收集片状态与风暴快照；只发已加载/已探索附近的片；预报 = `min(rainTime, thunderTime)` 与类型变化；后续可加概率预测字段。
- 协议 `"9"` → `"10"`。

### 4.2 Xaero 世界地图联动（反馈 2）

**事实核查**：

- Xaero 的模组**闭源**，GitHub 没有 `Xaero's World Map` 的官方源码仓库；可参考的开源项目只有附属模组：
  - [XaeroPlus](https://github.com/rfresh2/XaeroPlus)（开源，修改/扩展 Xaero 行为）
  - [XaeroWorldMapVisualExtras](https://github.com/AwesomeHippo/XaeroWorldMapVisualExtras)（MIT，视觉扩展）
- Xaero 官方 Maven 发布完整 jar（含 1.21.1 / 世界地图 1.47.0）：<https://chocolateminecraft.com/maven/xaero/map/xaeroworldmap-neoforge-1.21.1/>
- jar 内存在公开扩展 API（javap 核实）：
  - `xaero.map.WorldMap.mapElementRenderHandler`（`public static MapElementRenderHandler`）
  - `MapElementRenderHandler.add(ElementRenderer)`
  - `MapElementRenderer<E,C,R>` / `MapElementRenderProvider<E,C>` / `ElementRenderLocation.WORLD_MAP`
  - 这就是 Xaero 自己绘制路径点/玩家/领地元素的入口，不需要 mixin。

**集成方案**：

1. Gradle 增加可选 `compileOnly` 依赖（只在开发机启用，CI/普通构建不启用）：`xaero.map:xaeroworldmap-neoforge-1.21.1:1.47.0`，仓库 `https://chocolateminecraft.com/maven`。
2. 独立类 `client/compat/XaeroWorldMapOverlay`：只在 `ModList.isLoaded("xaeroworldmap")` 时通过反射/延迟类加载安装；未安装 Xaero 时零成本。
3. 渲染：注册一个 `MapElementRenderer`，元素类型 = 天气格（屏幕坐标 + 类型色 + 雨量 alpha）与风暴圆；在 `renderElement` 用 `GuiGraphics.fill` 绘制半透明矩形/圆近似；按 `ElementRenderInfo` 的缩放与地图坐标换算。
4. 配置：`client.toml [visual] xaeroWeatherOverlay`（true/false，默认 true，仅在世界地图存在时生效）。
5. **不打包、不反编译分发** Xaero 代码；README 注明可选依赖与来源。

**风险**：Xaero API 非稳定契约（版本升级可能破坏）；用反射兜底并在失败时禁用覆盖层；Xaero 世界地图与自有 GUI 都可以用，二者互不依赖。

## 5. WP4：兼容（effects 任意属性、API、Apothic Attributes）

### 5.1 Effects 任意属性

- `WeatherType.Effects` 新增 `List<AttributeMod> attributes`：
  `AttributeMod(ResourceLocation attribute, double amount, Operation operation, boolean only_when_exposed)`；
  `Operation = ADD_VALUE | ADD_MULTIPLIED_BASE | ADD_MULTIPLIED_TOTAL`。
- 服务端合成：按层收集 → 同属性同 operation 求和/取最强 → clamp amount `[-1000, 1000]` → 每玩家最多 16 个 modifier → 每属性固定 UUID → 天气结束/退出/死亡清理。
- `movementSpeed` 保留为便捷字段，内部转成 `minecraft:generic.movement_speed` 的 `ADD_MULTIPLIED_TOTAL`；两处都写时取更强。
- 安全：`[compat] effectsApplyAttributes`（true）、未知属性 id 告警一次、非法值忽略；文档列怪癖（飞行、攻速、生命上限）。
- 数据格式示例：

```json
"effects": {
```

### 5.2 API 扩展

- `WeatherApi.layersAt(ServerLevel, BlockPos)` → `List<WeatherLayerView>`（类型/雨/雷/强度/是否能在此降水）。
- `WeatherApi.forecast(ServerLevel, BlockPos, int horizonTicks)` → `List<ForecastStep>`（变化时间、下一类型、强度）。
- `WeatherApi.mapSnapshot(ServerLevel, BlockPos, int radius)` → 云图数据（供附属模组自绘）。
- 新事件公开；`StormRemoveEvent.Reason` 扩枚举（旧值不变）。
- 新文档 `docs/api-2.0.0-alpha.md`：方法签名、线程约束（服务端主线程）、协议版本、返回空列表的语义。

### 5.3 Apothic Attributes 分析结论

- **可行**：属性全部走 `BuiltInRegistries.ATTRIBUTE`，通用 `AttributeModifier` 即可寻址 `apothic_attributes:*`；无需编译依赖，运行期按 id 解析，不存在则告警跳过。
- 风险：Apothic 自己的派生属性/重算逻辑可能覆盖；百分比类属性需 `ADD_MULTIPLIED_BASE`；文档写明“支持标准 AttributeMap 语义，不保证专有派生属性”。
- 验证：装 Apothic 手动测试护甲/移速/暴击类属性，记录哪些生效。

## 8. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 协议升版导致旧客户端被拒 | README/更新日志写明必须同版本；`optional()` 只处理缺通道 |
| 合并/分裂导致存档膨胀或风暴暴增 | 冷却 + 每次检查上限 + `maxStormsPerDimension`；`/weather storm list` 观测 |
| 地形采样在未加载区块 | 只对已加载位置采样，`getHeight` 不会加载区块；失败时因子保持 1 |
| 渐变增加客户端开销 | 只在层集合变化时建立过渡；无变化零成本 |
| Xaero API 非稳定 | 独立类 + try/catch + 配置开关；失败自动禁用 |
| 属性修饰符冲突 | 固定 UUID + 每玩家上限 + 退出清理；文档说明 |
| 片模式演化与过滤冲突 | 演化前再走一次池/黑白名单判定；强制/锁定片不演化 |

回滚：每个里程碑独立可编译；配置开关可单独关闭新功能（地形/合并/分裂/演化/渐变/室内/地图/属性）。
